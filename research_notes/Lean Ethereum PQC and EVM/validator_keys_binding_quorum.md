# Ethereum consensus: validator identity-to-key binding, key lifecycle and quorum design (BLS today, post-quantum lean consensus planned). State as of 2026-10-21

Status tags: **[SHIPPED]** = live on mainnet / in the canonical spec; **[DECIDED]** = scheduled or adopted but not yet live; **[PROPOSED]** = written proposal (draft EIP, ethresear.ch design, PR); **[RESEARCH]** = exploratory, benchmarks, devnets, opinion. Dates are publication or last-update dates of the source unless stated otherwise.

## Q1. Today (BLS): how a validator key is bound at deposit, the role of withdrawal credentials, rotation, and rogue-key defence

### Takeaway
A validator's identity is its 48-byte BLS pubkey, fixed at the first processed deposit. That deposit carries a BLS signature over (pubkey, withdrawal_credentials, amount) under a fork-agnostic deposit domain, which serves as proof of possession against rogue-key attacks. Withdrawal credentials (0x00 BLS hash, 0x01 execution address, 0x02 compounding address) are a second, separate authority: since Pectra (May 7, 2025) the 0x01/0x02 address can trigger exits, partial withdrawals and consolidations from the execution layer. The signing key itself cannot be rotated in place. Moving to a new key means exiting, or depositing a new validator and consolidating into it.

### Inferences
- **Signing-key rotation does not exist today [SHIPPED behaviour, inferred from the spec].** No consensus operation modifies `Validator.pubkey`. The only key-changing operation, `BLSToExecutionChange`, changes the *withdrawal* credential, once, from 0x00 to 0x01. A deposit for an existing pubkey only tops up the balance. The practical "rotation" path since Pectra is: deposit a new validator with a new BLS key and 0x02 credentials, then send an EIP-7251 consolidation request from the old validator's withdrawal address (source → target). The old key exits and its balance moves to the new key. Otherwise, exit (EIP-7002 or voluntary exit) and re-deposit. The PQ registry post proposes a *new* operation for PQ keys (Q2), which confirms that no in-place mechanism exists.
- **Binding hierarchy today.** The deposit signature binds pubkey ↔ withdrawal_credentials ↔ amount at first registration (first processed deposit wins). From then on, two keys govern the validator: the BLS signing key (duties) and the withdrawal authority (0x00 BLS withdrawal key, or the 0x01/0x02 EL address). The EL address can exit, withdraw and consolidate, but cannot sign duties or change the signing key.
- Because the deposit domain carries no fork version and a zero genesis-validators-root, a deposit signature cannot be reused for another message type. It is valid across all forks of the chain.

## Q2. Post-quantum plan: registering hash-based (leanSig/XMSS) keys, migrating from BLS, rotating stateful keys

### Takeaway
As of Oct 2026, the plan of record is a **PQ public-key registry fork first** (EF milestone I*), letting validators attach a hash-based XMSS-family (leanSig/"leanXMSS") public key alongside their BLS key. The switch to PQ signatures for consensus follows "several forks later" (L*/M*), with core PQ infrastructure targeted around ~2029. The leading design (ethresear.ch, June 1, 2026) authenticates each registration with the **withdrawal credential**: an L1 signature from the 0x01/0x02 address, or the active BLS key for 0x00. It adds an XMSS proof of possession and a version/sequence field for rotation. A draft PQ-ready deposit contract (Aug 24, 2026) adds scheme identifiers and variable-length keys. Key lifetime, the hash function and the registry format are all still open.

  - **Rate limit:** example `MAX_PQ_REGISTRATIONS_PER_BLOCK = 16`, with excess queued in a mempool.
  - **Incentives (unsettled):** priority in the PQ activation queue, a temporary attestation-reward boost, or inactivity leak / forced exit near the deadline.
  - **Lifetime:** **2^32 slots** (≈1,632 years at 12 s). Exhaustion is implicit, with no bounds recorded in the registry. Activation windows align to **65,536-slot** boundaries (≈9 days).
  - **Hash agility:** Option A, a hash-function identifier per entry (re-register if a hash breaks). Option B, commit to 2–3 hashes up front (e.g., Poseidon1, BLAKE3, SHA-256), with keys of 104–156 bytes. Poseidon2 is flagged as low-maturity after recent attacks (eprint 2026/306).
  - **Numbers:** signature 3,112 B. KoalaBear field with degree-5 extension (123-bit provable security). 248-bit digests. Encoding: 46 chains, base 8. ~1,000 XMSS sig/s on an M4 Max. 2-to-1 recursion < 1 s. Final proof 128–350 KiB. Key generation takes hours on 8–16 cores; the only secret is a 32-byte seed. Production target ≈ **1M validators**.

### Inferences
- **The migration anchor is the withdrawal credential, not a STARK.** The leading registry design uses the 0x01/0x02 EL address (ECDSA today) or the existing BLS key to authorize a PQ key. Both are quantum-vulnerable, so the registry must be populated *before* a cryptographically relevant quantum computer exists. That is why it is staged early (I*) and why the PQ deposit contract can irreversibly close Scheme 0. Proving knowledge of a pre-image or seed with a STARK (zkMAC, hashed-BLS commitments) appears only in replies [RESEARCH], not in the main proposal.
- The **0x00 deprecation track** (EIP-8365 → EIP-8433 → sunset → removal of `BLSToExecutionChange` at the PQ fork) makes sense as a prerequisite. For 0x00 validators the only registration authority would be a BLS key that a quantum attacker can recover.
- **Rotation for stateful keys** is designed as re-registration with a monotonic version (proposal) plus aligned activation windows (65,536 slots). An explicit revocation record and two-layer certificate chains (Obol) are alternatives under discussion. No rotation mechanism is DECIDED.
- With lifetimes of 2^32 slots, exhaustion is practically irrelevant. Rotation is then driven by compromise, hash deprecation (agility) and operational migration, not leaf depletion. If shorter lifetimes are chosen (e.g., ~8 years), periodic re-registration becomes a protocol-level duty.

## Q3. Preventing key substitution: what binds a signature to a registered key and identity

### Takeaway
Today a signature is bound to (i) a message type, chain and fork through the domain in `SigningData`, and (ii) a validator identity through the **validator index** → registry pubkey lookup in the beacon state. Attestations carry committee bitfields, never pubkeys. The registry pubkey is immutable after its proof-of-possession-checked first deposit. EL-triggered operations bind to the identity through `source_address == withdrawal_credentials[12:]`. The PQ plan keeps this model: the registry entry is authenticated by the withdrawal authority plus an XMSS PoP, and the leanVM aggregate proves validity for exactly the keys in a signer bitfield.

### Cited Findings
- **[SHIPPED] Domain separation.** `compute_signing_root()` hashes the object root with a domain in `SigningData`. The domain combines a domain type (so "signatures made for one purpose cannot be re-used for a different purpose"), the fork version, and the genesis validators root ("uniquely identifies this particular beacon chain"). Deposits are the only fork-agnostic exception — [eth2book, 2026-01-13](https://eth2book.info/latest/part2/building_blocks/signatures/); [consensus-specs Electra (raw)](https://raw.githubusercontent.com/ethereum/consensus-specs/refs/heads/master/specs/electra/beacon-chain.md)
- **[SHIPPED] Index-based identity in aggregates.** A verifier rebuilds the committee from (slot, committee index) and filters it by `aggregation_bits` to get validator indices. It then fetches those validators' pubkeys **from the beacon state**, aggregates them, and verifies against the attestation data's signing root. Aggregates merge only with disjoint bits — [eth2book](https://eth2book.info/latest/part2/building_blocks/signatures/)
- **[SHIPPED] Registry immutability and PoP.** New pubkeys enter only after `is_valid_deposit_signature`. Later deposits to the same pubkey are balance top-ups with no signature or credential change — [consensus-specs Electra](https://github.com/ethereum/consensus-specs/blob/master/specs/electra/beacon-chain.md)
- **[SHIPPED] EL authority binding.** EIP-7002 withdrawal requests and EIP-7251 consolidation requests are processed only if the request's `source_address` equals `withdrawal_credentials[12:]` of the source validator. Consolidation targets must already be 0x02 — [consensus-specs Electra (raw)](https://raw.githubusercontent.com/ethereum/consensus-specs/refs/heads/master/specs/electra/beacon-chain.md)
- **[PROPOSED 2026-06-01] PQ binding.** `PostQuantumRegistration` is authorized by the withdrawal address (0x01/0x02) or the active BLS key (0x00), plus an XMSS PoP. A version field orders rebindings. The leanVM aggregate includes a **signer bitfield**, and "the circuit proves signatures exist for exactly that subset", because the CL "must know exactly who participated". Option A attaches a **hash-function identifier** to each registry entry — [ethresear.ch #25040](https://ethresear.ch/t/exploring-the-design-space-for-a-post-quantum-public-key-registry-for-ethereum-validators/25040)
- **[PROPOSED 2026-08-24]** The PQ deposit contract tags each deposit with a **scheme identifier** (0 = BLS), binding the key to its algorithm at registration — [crypto.news](https://crypto.news/ethereum-proposes-post-quantum-deposit-contract/)
- **[RESEARCH 2026-07]** In "Extremely Lean", the on-chain identity becomes a 5-byte deposit-tree index. Phase 2 rotates (re-anonymizes) keys daily, so the index-to-key link would be proven inside STARKs rather than stored in plain form — [Unchained, 2026-07-07](https://unchainedcrypto.com/vitalik-buterin-proposes-extremely-lean-ethereum-that-cuts-validator-state-by-95-using-zk-proofs/)

### Inferences
- **Key substitution is structurally hard today.** No message carries a pubkey that the verifier trusts. Pubkeys come only from `state.validators[index]`, which is written once, after a PoP. A substitution attack would need to (a) win the *first* deposit for a pubkey (the front-running vector that affects credentials, not signing keys) or (b) compromise the withdrawal address, which can exit, withdraw or consolidate but not re-key.
- In the PQ registry, substitution resistance depends on the withdrawal authority's signature, which is ECDSA or BLS and so quantum-vulnerable, plus version monotonicity. The PoP proves only possession of the new key; per the fetched summary, the post itself does not analyze malicious substitution or front-running. This is the weakest point and the reason for early registration.
- The signer-bitfield requirement keeps index-based accountability (slashing, inactivity) under SNARK aggregation. Without it, a valid aggregate could not attribute participation.

## Q4. Quorum and participation: 2/3 finality, committees, 3SF / lean finality, set size, MaxEB, entry/exit, accountability

### Takeaway
**[SHIPPED]** Gasper finalizes with 2/3-of-stake supermajority links between epoch checkpoints. Entry and exit are permissionless but rate-limited by stake-denominated churn (128–256 ETH/epoch since Electra). Accountability comes from slashing (initial 1/4096 of balance, a correlation penalty, a 36-day exit) and the inactivity leak, which restores a 2/3 active majority after >4 non-finalized epochs. **[RESEARCH]** Lean consensus is moving to 4 s slots, ~3-slot or 1–2-round finality (3SF-mini in devnets, a planned "PQ heartbeat", Minimmit/Live-Minimmit variants with 5f+1 / 80% quorums), and smaller per-slot signer counts (about 256–1024 or committee-based). Validator-set targets range from about 1M PQ keys in the registry to capped active sets of about 30k.

### Cited Findings
- **[SHIPPED] FFG supermajority.** A checkpoint is justified when "two-thirds of the total staked ether" votes for it. A supermajority link between successive checkpoints finalizes the earlier one — [ethereum.org Gasper, updated 2026-04-03](https://ethereum.org/developers/docs/consensus-mechanisms/pos/gasper/)
- **[SHIPPED] Inactivity leak.** It activates "when the chain has failed to finalize for more than four epochs", draining non-participating stake until inactive validators "control less than 1/3 of the total stake" — [ethereum.org rewards & penalties, updated 2026-09-28](https://ethereum.org/developers/docs/consensus-mechanisms/pos/rewards-and-penalties/); [Gasper page](https://ethereum.org/developers/docs/consensus-mechanisms/pos/gasper/)
- **[SHIPPED] Slashing.** Offences: two blocks for the same slot, surround vote, double vote. The initial burn is 0.0078125 ETH per 32 ETH, i.e. 1/4096, matching `MIN_SLASHING_PENALTY_QUOTIENT_ELECTRA = 4096`. A correlation penalty at day 18 scales with stake slashed in the surrounding window, and exit takes 36 days. The same page's intro still says "up to 1 ETH" (pre-Electra 1/32), an internal inconsistency — [ethereum.org rewards & penalties](https://ethereum.org/developers/docs/consensus-mechanisms/pos/rewards-and-penalties/); [consensus-specs Electra](https://github.com/ethereum/consensus-specs/blob/master/specs/electra/beacon-chain.md)
- **[SHIPPED] Entry/exit rate limits and MaxEB.** Churn is stake-denominated: `MIN_PER_EPOCH_CHURN_LIMIT_ELECTRA = 128 ETH`, `MAX_PER_EPOCH_ACTIVATION_EXIT_CHURN_LIMIT = 256 ETH`. MaxEB is 2048 ETH; 32 ETH is still the minimum activation balance — [consensus-specs Electra](https://github.com/ethereum/consensus-specs/blob/master/specs/electra/beacon-chain.md); EIP-7251 consolidations reduce validator count/bandwidth — [EF blog](https://blog.ethereum.org/2025/04/23/pectra-mainnet)
- **[SHIPPED, approximate] Scale today.** About 30,000 validators attest per slot to support fork choice (TokenPost, Sept 2026, secondary) — [TokenPost](https://www.tokenpost.com/news/technology/24599). The PQ registry post sizes its design for "about 1M validators" — [ethresear.ch #25040](https://ethresear.ch/t/exploring-the-design-space-for-a-post-quantum-public-key-registry-for-ethereum-validators/25040). *(Low-confidence secondary figures; no beaconcha.in snapshot fetched.)*
- **[DECIDED, not live] Glamsterdam (ePBS EIP-7732 + block-level access lists, 18 changes):** Sepolia fork 2026-10-06 (reported finalized). Hoodi ~2026-10-26/27 (set on the 2026-10-08 ACD call). - **[RESEARCH] 3SF.** Luca Zanolini (EF), 2025 Cambridge talk: 3SF finalizes "within just three slots after a proposal", vs 64–95 slots for Gasper — [talks.cam.ac.uk](https://talks.cam.ac.uk/talk/index/226648/). leanConsensus uses **3SF-mini**, targeting ~10 s average finality with 4 s slots; "3SF-mini may not be the final algorithm" (LambdaClass, Mar 2026) — [LambdaClass blog](https://blog.lambdaclass.com/finality-in-leanconsensus-how-ethlambda-implements-3sf-mini/)

### Inferences
- **The quorum is moving up as rounds go down.** Today's 2/3-of-stake (3f+1) FFG gives ~13–15 min finality. Minimmit-family designs reach 1–2-round finality but need 80% (5f+1) for fast finalization. Live- variants add liveness under ≥2f+1 participation. Any lean design will likely keep a 2/3 path or an inactivity-leak-style fallback for liveness. The specific combination is RESEARCH.
- **Safety under open entry/exit** still rests on stake-denominated churn limits (since Electra), so the signer set changes by only a small fraction per epoch. A PQ registry with activation windows aligned to 65,536 slots is consistent with keeping fixed, slowly changing signer sets per window. The window alignment is a rotation-cadence parameter; it is not stated to be a churn bound.
- **MaxEB is the bridge** from ~1M BLS validators to smaller active signer sets. It enables consolidation without lowering per-ETH security, and Orbit/rainbow-staking designs (Q5) depend on it.

## Q5. "Orbit"/rotating validator subsets and fixed vs dynamic signer sets

### Takeaway
Rotating subsets are a long-running RESEARCH thread with no adopted design. **Orbit SSF** (June 2024) samples an active set (~32k cap) by balance: validators with ≥T stake are always active, and a slowly rotating periphery of small validators fills the rest, with rewards rescaled to preserve per-ETH yield. Lean-consensus planning references "1 ETH Orbit staking", committee-based "PQ heartbeat" voting, and 256–1024 signatures per slot. The "Extremely Lean" idea pushes towards per-day fresh (anonymized) signer keys, i.e. highly dynamic signer identities over a stable deposit-index registry.

### Cited Findings
- **[RESEARCH 2024-06-28] Orbit SSF** (fradamt, credits Anders, Ansgar, Barnabé, Thomas). Goals: cap active validators at about 2^15 ≈ 32k, keep 32 ETH solo staking viable, ~20M ETH eventual economic security, 1/2-resilient under synchrony and 1/3 under partial synchrony. Sampling: p(S) = min(S/T, 1); rewards r(S) = R·max(1, S/T). E.g. T = 4096 ETH → ~30k active at D ≈ 120M ETH; explicit cap of ~40k (σ ≈ 1000). Stable core (large validators always active) plus a **slowly** rotating periphery, which avoids adversaries accumulating weight across fast-rotating committees. Economic security accumulates across slots to full security within roughly two epochs. Consolidation incentives: issuance I(D_a) = c√D_a and an extra per-validator yield term. It cites Vitalik's 8192-signatures-per-slot post as background. Key registration is not discussed — [ethresear.ch Orbit SSF](https://ethresear.ch/t/orbit-ssf-solo-staking-friendly-validator-set-management-for-ssf/19928)
- **[RESEARCH 2024-07] Replies:** dapplion called declining individual consolidation incentives "the missing piece" for MaxEB. alonmuroch raised whether Orbit privileges large pools and pushes them toward DVT — [ethresear.ch Orbit SSF](https://ethresear.ch/t/orbit-ssf-solo-staking-friendly-validator-set-management-for-ssf/19928)
- **[RESEARCH early 2026]** The Lean Consensus 2026 Plan lists "1 ETH Orbit staking" as an example under "smaller validators" — [HackMD](https://hackmd.io/@tcoratger/ryS1ElrWbx)
- **[RESEARCH]** The planned pq-devnet-5 "PQ heartbeat" uses committee-based voting with Goldfish — [leanroadmap.org](https://leanroadmap.org/). Vitalik (~Feb 2026) estimates 256–1024 hash-based signatures per slot — [X post](https://x.com/VitalikButerin/status/2027075026378543132?lang=en) (via snippet). Proposed committees of ~256–512 — [TokenPost](https://www.tokenpost.com/news/technology/24599)
- **[RESEARCH 2026-07]** "Extremely Lean": a daily STARK per validator and daily fresh, re-anonymized keys in phase 2 — [Unchained](https://unchainedcrypto.com/vitalik-buterin-proposes-extremely-lean-ethereum-that-cuts-validator-state-by-95-using-zk-proofs/)
- **[RESEARCH]** Minimmit assumes a known n and a predetermined leader schedule. Validator-set changes and epochs are not addressed — [Dankrad Feist](https://dankradfeist.de/tempo/2025/12/31/minimmit-simple-fast-consensus.html)
- **[PROPOSED 2026-06]** PQ key activation windows align to 65,536-slot boundaries (~9 days), a fixed cadence for when new or rotated keys become usable — [ethresear.ch #25040](https://ethresear.ch/t/exploring-the-design-space-for-a-post-quantum-public-key-registry-for-ethereum-validators/25040)

### Inferences
- The lean direction combines a **large, dynamic registry** (permissionless deposits, ~1M PQ keys, possibly 1 ETH minimum) with **small, fixed-per-period signer sets** (committees, Orbit samples, 256–1024 signers per slot) sampled from it. BFT-style protocols such as Minimmit/3SF need a known n per period, so per-epoch or per-window membership snapshots are the natural interface between the two.
- **Fixed vs dynamic:** today's Ethereum signer set is dynamic but churn-limited and snapshotted per epoch via committee shuffling. Every proposal found keeps membership changes slow relative to finality (Orbit's "slowly rotating periphery", churn limits, activation windows). The reason given is to prevent cumulative-weight attacks across committees.

### Gaps
- No 2025–2026 primary write-up of Orbit adapted to PQ/lean consensus was found, only the 2024 post and a one-line 2026 plan reference.
- "Rainbow staking" (heavy/light staker tiers) is mentioned only as a lean-consensus work bucket; details were not retrieved.
- No source specifies how a sampled/rotating committee member's XMSS key version is fixed for a period (e.g., snapshotted at window start).
